# 要件定義書：遠隔ICU eRN 勤務管理アプリ（iPad / オフラインファースト）

> 本書は開発を依頼するための要件定義書。実装者はこの文書だけを読めば設計に着手できることを目標とする。

> **改訂（2026-07-12）**：**ラウンド間隔は可変**であることを明記。ラウンドは固定スケジュールを持たず、eRN が任意のタイミングで開始・終了する。アプリは実測の開始/終了時刻と前ラウンドからの間隔を記録する（§3・§4.5・§5.3・§6 に反映）。

---

## 0. 一行サマリ

**多拠点・1シフト最大30患者を、eRN が「二検出器レース（eRN vs 現場）」の役割分担として管理し、1シフト内で複数回（既定4回）ラウンドしながら介入を記録し、蓄積データから proactive 選定の精度を経時的に上げる iPad アプリ。**

---

## 1. 背景・目的

### 1.1 前提の特殊性
遠隔ICU の eRN は通常のベッドサイド看護と2点で異なる。

1. **患者情報が間接**：カメラ / モニタ / EMR 経由でしか患者を見ない。
2. **第二の検出器が並走**：現場スタッフという別の悪化検出系が同時に動いている。

この2点から、シートの目的は「悪化の検出」ではなく **「二つの検出器のどちらを先に発火させるか＝役割分担の設計」** になる。これは proactive / reactive の分岐そのものであり、two-detector race model の実務実装にあたる。

### 1.2 目的
- 1シフト内で30患者に注意を枯らさず配分する。
- 1シフト内の複数回ラウンドの都度入力に耐える（30患者×4ラウンド＝最大120観測）。
- 感染治療状況を proactive トリガーの一つとして把握する。
- 全介入を「誰が先に気づいたか」付きで記録し、蓄積する。
- 蓄積データから **eRN 自身の proactive 選定の精度（先回りの的中率）** を計測・改善するループを回す。
- 同一データが threshold / race model の検証入力を兼ねる。

### 1.3 非目的（重要）
- EMR とのリアルタイム連携はしない（初版は匿名化手入力）。
- 多職種共有ツールではない（eRN 個人の管理・研鑽ツール）。
- 患者の網羅的電子カルテ化はしない（必要最小限のトリアージ情報のみ）。

## 3. 想定ユーザー・利用環境

- **ユーザー**：遠隔ICU の eRN（本人、単独利用）。
- **端末**：iPad（Safari / PWA インストール）。Apple Pencil の Scribble 入力に対応。
- **回線前提**：**オフラインファースト**。回線が不安定でも全機能が端末内で完結する。
- **利用単位**：1勤務（1シフト）＝1つの管理セッション。1シフト内で全患者を複数回ラウンド（**既定4回・設定で変更可**）。**ラウンドの実施タイミング・間隔は固定しない（可変）**：患者状態や業務状況に応じて eRN が任意の時刻に開始する。
- **同時管理患者数**：最大30。1ラウンドを短時間で捌ける入力速度が必須。

## 4. 情報設計の中核方針（実装者はここを最優先で理解する）

### 4.1 三層構造
30患者を等分に見ない。面積を差別配分する。

| 層 | 対象 | 表示 | 目的 |
|---|---|---|---|
| **roster 層** | 全患者 | 1行/患者・薄く広く | トリアージ（今どこを見るか） |
| **精査層** | proactive 対象のみ | 展開・厚く1枚 | 先回り監視・詳細把握 |
| **ログ層** | 介入発生ごと | イベント単位 | race 実測・蓄積 |

### 4.2 race 二値による層別
各患者は各ラウンドで次の2値を持つ。

- **proactive 対象**：eRN が先回りして見にいく（現場が拾いにくい悪化を持つ）。
- **reactive 待機**：現場が確実に拾うので、eRN は閾値アラートだけ持って待つ。

reactive 層に eRN の監視面積を割かないことが、30患者で注意を枯らさない条件。race 層はラウンドごとに再評価され、悪化/安定で proactive⇄reactive を移動しうる。

### 4.3 感染治療状況は独立タブにしない
感染は **proactive トリガーの一種** として扱う。roster 層に警告フラグとして浮かせ、詳細は精査層で持つ。主なトリガーは device-days、DOT、de-escalation due の3つ（後述）。

### 4.4 拠点軸
roster に拠点タグ（KRC / SMM）を持たせる。拠点ごとに現場検出力（人員・経験・体制）が異なるなら、proactive 配分を拠点で傾けられるようにする（検出力が低い拠点ほど eRN が先回り側に回る）。

### 4.5 ラウンド運用の中核方針（入力負荷が最大の敵）
1シフト＝複数ラウンドの反復。30患者×4回で最大120観測が発生する。**全項目を毎回打たせたら蓄積は死ぬ。** よって設計原則は「前回ラウンド値を引き継ぎ、差分だけ触らせる」。

- reactive の大多数は「変化なし」1タップで確定（値を carry-forward）。
- proactive と変化ありだけ実入力。
- 「変化なし」確定でも観測レコードは残す（監視した事実の記録＋トレンドの連続点＋race の観測点になる）。
- **ラウンド間隔は可変**：ラウンドをタイマーやスケジュールで自動開始しない。eRN が「ラウンド開始」を明示的に押した実測時刻を記録し、前ラウンドからの間隔を表示する。既定回数は目安であり、超過分の追加ラウンドも（確認の上で）開始できる。間隔・回数の実測値は蓄積解析の入力になる。

## 5. 機能要件

### 5.1 シフト管理
- シフトを新規作成（日付、開始/終了、担当拠点複数選択、ラウンド回数）。
- 過去シフトの閲覧（読み取り専用）。
- シフト単位で全データがスナップショット保存される。

### 5.2 Roster 画面（トップ / 各ラウンドのメイン）
- 患者を1行1患者で一覧表示。
- 各行に表示する要素：
  - 拠点タグ（KRC / SMM）
  - 病床 / 匿名化ID
  - **race 層**（proactive / reactive をトグルで切替可能）
  - **EWS トレンド**：**当該シフト内 R1→R2→R3→R4 の軌跡**（スパークライン＋直近ラウンド間の変化矢印）。急性悪化はラウンド間差分に出るため、これがサーベイランスの主軸。
  - 感染フラグ（下記トリガーのいずれかが立つとアイコン点灯）
  - **ラウンド確認状態**：未確認 / 変化なし確定 / 更新済
- **ソート**：リスク順（最新ラウンドの EWS ＋ **ラウンド間の悪化幅** ＋ 感染フラグの合成スコア）で自動降順。じわじわ悪化が上に来る。
- 手動 proactive はピン留め。

### 5.3 ラウンドモード（都度入力の本体）
1ラウンド＝全患者を1周する掃引。これを短時間で終える UX を最優先で実装する。

- ラウンド N は **eRN が任意のタイミングで開始**する（間隔は可変・固定スケジュールなし）。開始時刻は自動記録され、前ラウンドからの実測間隔が表示される。
- ラウンド N を開始 → roster がリスク順で並ぶ。各行は **ラウンド N-1 の値でプリフィル済み**。
- 各行の操作：
  - **「変化なし」1タップ** → 前回値を carry-forward して confirmed。
  - **行をタップ → クイックシート**（前回値プリフィル）で差分だけ編集 → updated。
- **進捗インジケータ**：確認 12/30 のように残数表示。周り切りを保証する。
- **proactive 患者は blanket 確定不可**：必ず開いて更新（"要確認" マーク）。
- ラウンド終了で全患者に PatientRound が1件ずつ生成される（変化なし含む）。
- 次ラウンドは最新値からまた再開。

### 5.4 感染治療状況（精査層で展開）
患者ごとに保持。roster にはトリガーのみ上げる。ラウンドを跨いで持続（device-days は自動加算）。

**保持項目**
- 感染源 / 疑い部位、起因菌（複数可）
- 培養状況（未提出 / 結果待ち / 陽性 / 陰性）
- 抗菌薬（薬剤名、開始日、**DOT 自動計算**、スペクトラム広/狭）
- de-escalation フラグ（未 / 検討可 / 済）
- **device-days**：CVC / 尿カテ / 人工呼吸それぞれの留置日数（自動カウント）
- 感染系トレンド：発熱、WBC、CRP、PCT の推移（任意）

**roster に上げるトリガー（自動判定・閾値は設定変更可）**
| トリガー | 条件 | 意味 |
|---|---|---|
| device-days 警告 | 各デバイスが閾値日数超過 | CLABSI/CAUTI/VAP リスク。現場が見落としやすい経時リスク |
| DOT 警告 | 抗菌薬が規定日数到達 | 期間見直し |
| de-escalation due | 培養陽性かつ広域継続 | 狭域化提案タイミング |

感染フラグ＝proactive 候補として直結させる。

### 5.5 介入クイックログ（蓄積の生データ源）
介入発生ごとに最小タップで記録。**1介入＝数タップで完了。**

- 患者（roster から選択）、**round_id（自動：現ラウンドに紐付け）**、timestamp（自動）
- **trigger source**：`eRN発` / `現場発` / `アラート発` / `device起因`（1タップ）← race 生データ
- **category**：`proactive` / `reactive`（1タップ）
- 領域タグ：呼吸 / 循環 / 感染 / 鎮静 / その他
- 内容（自由記述・任意・Scribble 可）
- **outcome**：`介入要だった` / `空振り`（1タップ）← 精度計測に必須

### 5.6 race フリップ記録（proactive 選定＝検出器の起動イベント）
patient の race 層が **reactive → proactive に切り替わった瞬間**を1イベントとして自動スナップショット。「現場より先に検出器を起動した」瞬間の生データであり、precision 計算と race model の中核入力。

- from / to、切替ラウンド、時刻
- 選定時の患者特徴：EWS、device-days、DOT、鎮静有無、拠点、時間帯（日勤/夜勤）、現場体制（任意）
- 選定理由タグ（複数可）
- そのシフト内で実際に介入したか（5.5 outcome と突合）

### 5.7 シフト終了サマリ
- 総介入数、proactive / reactive 比
- **proactive 的中率**：reactive→proactive フリップのうち実際に介入要だった割合
- **取り逃し**：現場発だった悪化のうち proactive にしていなかった件数
- trigger source 内訳、拠点別内訳、ラウンド別内訳

### 5.8 蓄積ダッシュボード（精度向上ループの可視化）
複数シフト横断。**これがユーザーの精度を上げる本体。**

- **proactive precision の推移**（シフトを重ねるほど的中率が上がるか）
- **race 勝率の分解**：特徴別（時間帯 × 鎮静 × 拠点 × ラウンド番号）に eRN が現場より先に気づけた割合
- **フィードバック提示**：precision が高い条件 / 空振りが多い条件を言語化 → 次シフトの選定補正へ
- 感染介入の内訳（device-days / DOT / de-escalation）
- **エクスポート**：全 PatientRound・全介入・全 race フリップを CSV/JSON（threshold/race model の解析入力を兼ねる）

### 5.9 精度向上ループの論理（実装者向け）
1. 各 race フリップ・各介入で、発火時点の患者特徴とラベル（trigger source / outcome）をスナップ。
2. 「どの特徴が eRN 先行を予測したか」を集計 → two-detector race の eRN 側発火閾値の実測チューニング。
3. 結果を次シフトの選定基準へフィードバック。
4. proactive 選定の precision / recall が経時改善 = 蓄積で精度が上がるシステム。

> 初版は自動最適化不要。集計・可視化・人間が読むフィードバックで成立させる。自動最適化は将来拡張。

## 6. データモデル

```
Shift
  id, date, start_at, end_at, facilities[], round_count(default 4)

Round                        // シフト内のラウンド。間隔は可変：
  id, shift_id, round_number, // started_at/ended_at は実測時刻
  started_at, ended_at        // （スケジュール値ではない）

Patient                      // シフト内の永続ID。ラウンド間で不変・実名なし
  id, shift_id, facility(KRC|SMM), bed_label, anon_id,
  age, dx_summary

PatientRound                 // 患者×ラウンドの観測。ここが毎ラウンド増える
  id, patient_id, round_id,
  ews,
  race_layer(proactive|reactive),
  infection_trigger_snapshot { device_warn, dot_warn, deesc_due },
  entry_status(carried|updated),   // 「変化なし」確定 or 更新
  note

InfectionRecord              // Patient に1:1・ラウンドを跨いで持続
  patient_id,
  source, organisms[],
  culture_status(none|pending|positive|negative),
  antimicrobials[]  // [{name, start_date, dot, spectrum(broad|narrow)}]
  deescalation(none|due|done),
  device_days { cvc, foley, vent },
  infection_labs[]  // [{t, wbc, crp, pct, temp}]  任意

Intervention                 // 介入イベント
  id, patient_id, round_id, shift_id, timestamp,
  trigger_source(eRN|floor|alert|device),
  category(proactive|reactive),
  domain(resp|circ|infection|sedation|other),
  note, outcome(needed|miss)

RaceFlip                     // reactive→proactive の切替＝検出器起動イベント
  id, patient_id, round_id, from, to, at,
  features { ews, cvc_days, foley_days, vent_days, dot_max,
             sedation(bool), facility, time_block(day|night),
             floor_context(text) },
  reason_tags[],
  resulted_in_intervention(bool)   // シフト終了時に突合
```

- **匿名化**：Patient は実名・カルテ番号を保持しない（anon_id と bed_label のみ）。
- EWS と race_layer は **Patient ではなく PatientRound** が持つ（ラウンド時系列）。

## 11. 受け入れ基準（抜粋）

- 回線を切っても全機能が動く。
- 30患者を登録してもリスト操作が重くならない。
- **ラウンドを任意のタイミングで開始・終了でき（間隔可変）、実測の開始時刻と前ラウンドからの間隔が記録・表示される。**
- **各ラウンドで前回値がプリフィルされ、reactive 患者を「変化なし」1タップで確定できる。**
- **1ラウンド（30患者）を短時間で周り切れ、確認残数が可視化される。**
- EWS が当該シフト内のラウンド軌跡（R1→R4）で表示される。
- 1介入を5秒以内に記録でき、現ラウンドに紐付く。
- reactive→proactive フリップ時に患者特徴が自動スナップされる。
- シフトを閉じると proactive 的中率が自動算出される。
- 複数シフト蓄積後、precision の経時推移が1画面で読める。
- 患者実名を一切保存しない。
